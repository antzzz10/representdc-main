**Do not deploy this commit with analytics enabled yet.** I found **2 BLOCKERs and 2 MATERIAL findings**. The nine analytics tests pass, but they do not exercise the real PostHog SDK or network requests.

1. **BLOCKER — Click identifiers escape the filter through SDK-generated properties.** [index.html](index.html:47) deletes `gclid` and `$initial_gclid`, but PostHog also derives `$session_entry_gclid` and similar properties from the entry URL; the regex does not match that prefix. The current SDK also recognizes `oppref` and `bfcid`, neither of which is on the list. Thus, for example, a visit with `?gclid=...` can send the identifier even though `$current_url` is cleaned. The same gap applies to properties generated inside `$set_once`. This contradicts the decision note’s deletion claim. See PostHog’s [campaign parameter definitions](https://github.com/PostHog/posthog-js/blob/main/packages/browser-common/src/utils/event-utils.ts) and [session-property construction](https://github.com/PostHog/posthog-js/blob/main/packages/browser/src/session-props.ts).

2. **BLOCKER — Search terms can leave as a separate property.** [index.html](index.html:62) strips a query from `$referrer`, but does not remove PostHog’s `ph_keyword`, `$initial_ph_keyword`, or `$session_entry_ph_keyword`. If a search engine supplies a referrer containing its `q` or `p` parameter, the SDK extracts the search words into those properties. They can include sensitive text and directly contradict “Nothing a visitor types” and “Nothing from the address except campaign tags.” Whether the referrer contains the query depends on the referring site’s and browser’s referrer policies. [PostHog’s extraction code](https://github.com/PostHog/posthog-js/blob/main/packages/browser-common/src/utils/event-utils.ts) and [session-property code](https://github.com/PostHog/posthog-js/blob/main/packages/browser/src/session-props.ts) show the path.

3. **MATERIAL — Early page views can be attributed to the wrong route and campaign.** [analytics.js](src/lib/analytics.js:143) discards `pathname` and queues only `capture('$pageview')`. While the async SDK is still loading, a visitor can navigate to a second route. When the queued captures replay, PostHog constructs their URL and campaign properties from the *then-current* browser location, so both page views can appear on the second route and the landing campaign can be lost. This undermines the principal attribution claim. The same timing can affect SDK-generated URL properties on queued clicks.

4. **MATERIAL — Campaign values are neither reliably limited to 100 characters nor guaranteed to be non-identifying.** [index.html](index.html:69) truncates `utm_*` and `$initial_utm_*`, but not SDK properties such as `$session_entry_utm_source`. Those can retain longer values. Also, the five allowed UTM values are arbitrary: a URL such as `?utm_term=someone%40example.com` or a unique identifier is deliberately sent, up to the applicable limit. The decision note should not claim that nothing typed or no per-click identifier can reach PostHog without qualifying this exception. [PostHog’s session-property construction](https://github.com/PostHog/posthog-js/blob/main/packages/browser/src/session-props.ts) supplies the prefixed properties.

5. **NOTE — The tests establish the filter’s behavior on invented events, not the privacy guarantee.** [analytics.test.mjs](scripts/analytics.test.mjs:43) uses a stub that never loads the SDK; it checks selected config values and manually invokes `before_send`. It cannot establish actual cookies or storage, SDK-generated properties, requests outside event capture, click delivery, React routing, or page-view attribution. Its sample omits the properties in the findings above. The decision note’s broader description of what the tests cover is therefore overstated.

The `before_send` hook **is the appropriate event hook** for the snippet-loaded SDK, and the current SDK constructs top-level `$set_once` before invoking it; this code also checks the nested forms. That does not cover unrelated network traffic. The explicit settings disable the named capture features, and `advanced_disable_flags` currently suppresses ordinary remote-config loading for this generic snippet; it is not evidence that all possible SDK traffic or external dependencies are disabled. `persistence: 'memory'` is distinct from PostHog’s dedicated cookieless mode. The dynamically loaded SDK is unpinned, so these observations should be verified against the actual served version before release. [PostHog SDK source](https://github.com/PostHog/posthog-js/blob/main/packages/browser/src/posthog-core.ts), [remote-config loader](https://github.com/PostHog/posthog-js/blob/main/packages/browser/src/remote-config.ts), and [SDK security guidance](https://posthog.com/docs/libraries/js/security).

The member lookup’s own call sites send the control name rather than the selected value or typed name. No files were modified. The sister site was not independently audited, so these findings should not be assumed to describe its deployed behavior without checking it.

**DO NOT SHIP.** The sitemap parser can associate a headline with the wrong link, and broken sitemap or paginated-feed responses can be reported as healthy.

- **MATERIAL — A malformed sitemap can pair one story’s link with another story’s title and date.** [feeds.mjs](scripts/news/feeds.mjs:209) checks only for a closing `</urlset>`, while [the entry regex](scripts/news/feeds.mjs:222) can span two entries. For example, if the first entry contains `<url><loc>https://www.washingtonsun.com/story-a</loc>` but is missing `</url>`, followed by a complete entry for story B with its title and date, parsing produces **story A’s link with story B’s title and date**. The HTTPS and host checks and downstream article gate accept that combination; it can reach the public page and permanent archive.

- **MATERIAL — Broken sitemap content can pass source health as an empty feed.** [feeds.mjs](scripts/news/feeds.mjs:251) returns `no-items` whenever parsing yields nothing, and [fetchAllFeeds](scripts/news/feeds.mjs:339) converts that to `ok`. For example, `<urlset><url><loc>https://www.washingtonsun.com/a</loc><news:title>Story</news:title></urlset>` is truncated inside an entry but contains the closing root tag. It yields zero items and counts as healthy in G5, potentially allowing a quiet-day publication when all other news sources failed. A populated sitemap whose entries are all rejected has the same health result.

- **MATERIAL — Repeated pagination failures never trigger the source-failure alert.** A successful page 1 followed by HTTP 500 on page 2 returns `status: 'ok', partial: true` at [feeds.mjs](scripts/news/feeds.mjs:289). Both [G5](scripts/news/gates.mjs:160) and [feed-health tracking](scripts/news/archive.mjs:169) inspect only `status`. Thus a persistent failure to retrieve the older stories clears `failingSince` on every published run, although recovering those stories is the purpose of paging. The partial flag appears in the run record, but does not surface through the sustained-failure alert.

- **MATERIAL — An unreadable later page can end paging without even setting `partial`.** At [feeds.mjs](scripts/news/feeds.mjs:290), `no-items` is treated as a normal end. A page such as `<rss><channel><item><title>Story</title><pubDate>Tue, 24 Nov 2026 12:00:00 GMT</pubDate></item></channel></rss>` contains an item but no readable link, so `parseItems` drops it; page 3 is never requested and the result has no `partial` flag. Similarly, a later page containing only unparseable dates is counted together with page 1’s valid dates, masking that page’s failure.

- **NOTE — The new tests miss these failure modes.** [feed-sources.test.mjs](scripts/eval/feed-sources.test.mjs:86) checks a missing `</urlset>`, but not malformed entries with a closing root, cross-entry field mixing, rejected-only sitemaps, or the downstream health result. Its paging tests cover HTTP and visibly truncated failures, but not unparseable items or dates on later pages, nor sustained `partial` health tracking.

I found no ISO-date incompatibility in the inspected article gate, archive, or hand-link window calculations. The `getTag('loc')` expression does **not** match a normal `<image:loc>` tag; the cross-entry issue above comes from the enclosing entry regex and incomplete structural validation. The configured Sun source makes one fetch call per scan, although automatic HTTP redirects could entail additional requests. Newsletter fetching retains the same default single-page path.

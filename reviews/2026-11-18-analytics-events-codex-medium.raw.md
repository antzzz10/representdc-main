**Do not enable the PostHog key yet.** I found one BLOCKER and two MATERIAL findings. The nine offline tests pass, but they do not exercise the real PostHog SDK or browser network traffic.

1. **BLOCKER — Per-click identifiers can escape through PostHog’s session-entry properties.** [index.html:47](index.html:47) deletes bare names such as `fbclid` and `$initial_fbclid`, but not names such as `$session_entry_fbclid` or `$session_entry_gclid`. PostHog documents session-entry click-ID properties in its [event taxonomy](https://github.com/PostHog/posthog/blob/master/posthog/taxonomy/taxonomy.py). Those values are plain strings, so the URL-cleaning branch also leaves them untouched. This contradicts the decision note’s promise that per-click identifiers are deleted. The same filter also accepts arbitrary values in the five permitted UTM fields: an email address or unique identifier placed in `utm_term`, for example, is sent, truncated to 100 characters. Thus “nothing a visitor types” and “no per-click identifier” cannot be guaranteed for arbitrary incoming URLs.

2. **MATERIAL — Events can be lost when a visitor follows a link before the SDK finishes loading.** [src/lib/analytics.js:35](src/lib/analytics.js:35), [index.html:75](index.html:75). The snippet initially queues `capture` calls in JavaScript memory. If a visitor immediately follows a same-tab link to the tracker, candidates, newsletter, or another site, the document can unload before `array.js` loads and drains that queue. The click event is then lost. Even after loading, delivery on navigation is best effort; the [SDK’s capture documentation](https://github.com/PostHog/posthog-js/blob/main/packages/types/src/capture.ts) describes transport and unload limitations. Consequently the named “opened” events are click attempts, not proof that a destination opened, and their counts will understate some departures.

3. **MATERIAL — Privacy tests do not prove the documented privacy guarantees.** [scripts/analytics.test.mjs:43](scripts/analytics.test.mjs:43), [decisions/2026-11-18-analytics-events.md:56](decisions/2026-11-18-analytics-events.md:56). The test extracts the callback from a stub and supplies a hand-built event; it never loads the SDK, observes its actual event shapes or requests, checks storage, or tests remote configuration. It therefore misses the session-entry identifiers above and cannot establish that only campaign tags leave the browser. The stated stand-in browser check likewise cannot establish the real SDK’s behavior. A real-SDK network and storage check with representative URL, referrer, and navigation fixtures is needed.

4. **NOTE — Pageview and click attribution have narrower meanings than the note suggests.** [src/components/TrackPageviews.jsx:8](src/components/TrackPageviews.jsx:8), [src/lib/analytics.js:109](src/lib/analytics.js:109). Pageviews fire on **pathname changes**, not every router navigation: query-only and fragment-only changes are intentionally ignored. Redirect routes can also produce a view for the redirecting path and another for the destination. Link events run in capture phase, before it is known whether navigation will be prevented; any link inside an article’s table-of-contents `<nav>` is classified as `nav`, even though it is not the site menu. These distinctions matter when interpreting the decision note’s “one page view per page” and menu/page labels.

5. **NOTE — The filter does not enforce its broad URL claim.** [index.html:62](index.html:62). It cleans only string values beginning with `http://` or `https://`, plus the specific `$set` and `$set_once` containers it explicitly visits. Relative URLs, URL-encoded or embedded URLs, other nested structures, and arbitrary path text are not generally sanitized. The current application call sites do not deliberately send typed lookup text or link text, but the callback is not a general guarantee that such data can never be sent.

`before_send` **is the documented hook** for modifying browser SDK events, including with the HTML snippet; the code explicitly visits both top-level and property-nested `$set_once` and will clean an absolute `$initial_referrer` there. That does not cover non-event requests or prove all future SDK payload shapes. PostHog’s [privacy documentation](https://github.com/PostHog/posthog.com/blob/master/contents/docs/privacy/data-collection.mdx) describes the hook.

The configuration explicitly disables the listed autocapture, replay, heatmap, performance, survey and flag features, and PostHog’s [current source](https://github.com/PostHog/posthog-js/blob/main/packages/browser/src/posthog-core.ts) treats `memory` as in-memory persistence. I cannot verify the deployed project’s remote settings or prove the absence of every storage or network operation from the stub tests. The script is also unpinned, so future SDK changes can alter behavior without a repository change.

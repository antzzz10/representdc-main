**Recommendation: do not ship yet.** I found two BLOCKER and four MATERIAL issues affecting archive preservation, the article set checked by the judge, seed accuracy, and feed alerts.

1. **BLOCKER — A missing archive is treated as a first run even after memory exists.** `scripts/fetch-news.mjs:140`, `scripts/fetch-news.mjs:360`, `scripts/news/publish.mjs:143`  
   If the archive is deleted from `gh-pages` after a successful run—or between the initial read and a push retry—the next publish substitutes the old seed. The growth check receives `null`, so it permits writing an archive that has lost every later confirmation. An absent seed also silently becomes an empty archive. **Fix:** distinguish an explicitly authorized bootstrap from an unexpected missing file, fail closed if an archive previously existed, and compare retries against the initially read archive as well as the current branch. Test deletion both before a run and between its read and push.

2. **BLOCKER — A summary can be published beside different headline text from what the judge saw.** `scripts/fetch-news.mjs:350`, `scripts/fetch-news.mjs:363`, `scripts/news/archive.mjs:218`  
   The retry check compares links only. For example, this run summarizes and judges a first-seen headline; a concurrent run records the same link with a different headline in pending; on retry, this run confirms and displays the pending headline. The links match, so the summary remains live even though the judge saw different text. **Fix:** compare the complete ordered article objects used by the summary and judge with those actually being published; withhold on any difference. Add a production-path retry test with the same link and changed title.

3. **MATERIAL — The seed permanently confirms plainly off-topic entries.** `scripts/news/seed-archive.json:69`, `scripts/news/seed-archive.json:125`  
   “The 51st’s first crossword puzzle” and “The 51st in print!” are seeded as confirmed, although the relevance rules exclude community and human-interest stories unrelated to DC autonomy. They will never be re-judged and remain in the permanent record. The builder counts two historical publications as proof of relevance (`scripts/news/build-seed-archive.mjs:64`), which reproduces repeated filter errors. **Fix:** review and curate the seed against the current relevance standard before bootstrap, including the other potentially local-only entries; retain evidence for exclusions and approvals.

4. **MATERIAL — Feed failures can go untracked indefinitely when publishing fails.** `scripts/fetch-news.mjs:126`, `scripts/fetch-news.mjs:159`, `scripts/news/archive.mjs:272`  
   `failingSince` is persisted only in a successful archive publish. If one source is down while the relevance API repeatedly fails, each run calculates a new first-failure time but writes none of them; after recovery of the API, the source starts a fresh two-day clock. If every feed fails, G5 returns before health is even calculated. **Fix:** persist health independently and safely on failed runs, or use another durable alert state that does not require publishing article data. Test consecutive failed pipeline runs and all-source failure.

5. **MATERIAL — The alert closes while a source is still failing.** `.github/scripts/news-feed-alert.sh:47`, `scripts/fetch-news.mjs:159`  
   An empty alert list means no source has failed for *two days*, not that every source is healthy. If source A recovers while source B has failed for one day, the script closes the issue and announces that every source fetched; B receives no issue until its own clock reaches two days. **Fix:** pass actual failing-source state separately from the thresholded list, and close only when all sources have recovered. Test this handoff between failures.

6. **MATERIAL — GitHub command failures are reported as successful alert actions.** `.github/scripts/news-feed-alert.sh:84`, `.github/scripts/news-feed-alert.sh:94`  
   Failed issue edits, comments, closes, label creation, and issue creation are suppressed; the script exits zero and logs success even when no alert exists or an existing issue is stale. For example, a permission or transient API failure on creation leaves a dead source unreported with no actionable failure indication. **Fix:** check each command’s result, log a clear failure and return a nonzero status for the already `continue-on-error` workflow step; ensure the next run retries without duplicate comments or issues. Add mocked `gh` failure tests.
